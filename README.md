# URL Shortener

HTTP-сервис сокращения ссылок: принимает длинный URL и выдаёт короткий код, по коду перенаправляет на исходный адрес.

Исходное задание — [docs/00_task.md](docs/00_task.md).

## Запуск

Нужен только Docker.

```bash
cp .env.example .env
docker compose up --build
```

Поднимаются три сервиса: приложение, PostgreSQL и Redis. Приложение ждёт, пока база пройдёт healthcheck, накатывает миграции и начинает слушать `:8080`.

Проверка:

```bash
curl -i localhost:8080/health
```

Остановка с удалением данных: `docker compose down -v`.

## API

### POST /shorten

```bash
curl -X POST localhost:8080/shorten \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com"}'
```

```json
{"short_url": "http://localhost:8080/abc123"}
```

Повторный запрос с той же ссылкой возвращает **тот же** код и новой записи не создаёт. Ответ `200` в обоих случаях: клиенту не сообщается, была ссылка в хранилище или нет.

### GET /{code}

```bash
curl -i localhost:8080/abc123
```

```
HTTP/1.1 302 Found
Location: https://example.com
Cache-Control: no-store
```

`302`, а не `301`: постоянный редирект клиент вправе закэшировать навсегда, и ссылку уже не отозвать.

### GET /health

```json
{"status": "ok"}
```

При недоступной базе — `503` и `{"status": "degraded"}`. Redis в проверку не входит: без кэша сервис работоспособен.

### Ошибки

Тело ошибки одинаково для всех случаев:

```json
{"error": {"code": "invalid_url", "message": "url must be an absolute http or https URL"}}
```

| Ситуация | Код | `error.code` |
|---|---|---|
| Метод не поддержан для этого пути | `405` | `method_not_allowed` |
| Тело больше 16 КБ | `413` | `payload_too_large` |
| `Content-Type` задан и это не JSON | `415` | `unsupported_media_type` |
| Тело не разбирается как JSON либо это не объект | `400` | `malformed_json` |
| Объект разобран, но значение `url` не годится | `422` | `invalid_url` |
| Короткий код не найден | `404` | `not_found` |
| База недоступна или запрос к ней не уложился в срок | `503` | `service_unavailable` |
| Непредвиденная ошибка или паника | `500` | `internal_error` |

Граница `400`/`422`: `400` — объект получить не удалось, разбирать нечего; `422` — объект получен, поле прочитано, значение не подходит. Полный контракт с обоснованием каждого статуса — в [docs/01_requirements.md](docs/01_requirements.md).

## Архитектура

```
Handler → Service → Repository → PostgreSQL
             └────→ Cache      → Redis
```

Cache — не слой, а вторая исходящая зависимость сервиса наравне с репозиторием: оба отдают ссылку по коду и друг о друге не знают. Репозиторий и кэш — интерфейсы, у каждого две реализации: настоящая и подставная (`Memory`, `Noop`). На них же строятся тесты, отдельных моков в проекте нет.

**Короткий код** — 6 случайных символов base62 из `crypto/rand`, не связанных со ссылкой. Пространство 62⁶ ≈ 56.8 млрд. Усечённый хеш URL не используется: его коллизию нечем разрешить, а у случайного кода конфликт ловит `UNIQUE` и повторная попытка берёт другое значение.

**Дедупликация** — по SHA-256 нормализованной ссылки, а не по самой ссылке: хеш фиксированной длины и под уникальным индексом.

**Гонки** разрешает база, а не блокировка в Go: два уникальных ограничения, и конфликт по `url_hash` означает «ту же ссылку успел записать параллельный запрос» — читаем существующую запись, а по `short_code` — «совпали два случайных кода», генерируем новый. Различаются они по коду ошибки `23505` и имени ограничения, а не по тексту сообщения.

## Выбор технологий

**PostgreSQL** — ссылки должны переживать перезапуск, а нагрузка здесь — чтение по первичному ключу. Реляционная база даёт нужное уникальными индексами, без которых пришлось бы городить блокировки в приложении.

**pgx напрямую, без `database/sql`** — драйвер отдаёт структурированную ошибку `*pgconn.PgError` с полем `ConstraintName`. На нём держится различение двух конфликтов; через прослойку то же доступно лишним слоем и с конвертацией типов, которая ничего не даёт.

**golang-migrate, миграции внутри бинарника** — схема едет вместе с кодом через `//go:embed` и накатывается самим сервисом до начала прослушивания порта. Вариант с `docker-entrypoint-initdb.d` отклонён: он срабатывает один раз при создании пустой базы, и после правки схемы у проверяющего осталась бы старая.

**Redis как кэш перед базой** — переходов кратно больше, чем созданий. Кэш не является точкой отказа: при недоступности запрос идёт в базу, ответ клиенту не меняется. Промахи кэшируются тоже, иначе перебор несуществующих кодов проходит мимо кэша и бьёт прямо в Postgres.

**Стандартная библиотека вместо веб-фреймворка** — `net/http` с версии Go 1.22 умеет методы и параметры пути (`GET /{code}`), а `slog` даёт структурные логи. Двух эндпоинтов недостаточно, чтобы фреймворк окупил зависимость.

**Без OpenAPI и кодогенерации** — три эндпоинта не окупают спецификацию, генератор и сгенерированный код. Контракт уже описан в требованиях вместе с обоснованием каждого статуса, а машиночитаемая схема стала бы вторым его источником и разошлась бы с первым. Цена решения — нет готового клиента и страницы документации для внешнего потребителя; при росте числа эндпоинтов выбор стоит пересмотреть.

Обоснования остальных решений — таймауты и их иерархия, размер пула, зарезервированные коды, политика логирования — в [docs/02_design.md](docs/02_design.md).

## Конфигурация

Переменные окружения читаются из `.env` (см. `.env.example`):

| Переменная | Обязательна | Назначение |
|---|---|---|
| `BASE_URL` | да | префикс, из которого собирается `short_url` |
| `DB_CONNECTION` | да | строка подключения к PostgreSQL, включая `pool_max_conns` |
| `SERVER_PORT` | нет, `8080` | порт HTTP-сервера |
| `LOG_LEVEL` | нет, `info` | `debug`, `info`, `warn`, `error` |
| `REDIS_ADDRESS` | нет | адрес Redis; пустое значение — работа без кэша |

`POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` нужны контейнеру базы и должны совпадать с тем, что записано в `DB_CONNECTION`.

Таймауты, лимиты размеров и TTL кэша заданы константами в коде, а не переменными окружения: это решения дизайна с проверенной иерархией (запрос к БД < контекст запроса < `WriteTimeout` < shutdown), и возможность задать их снаружи позволила бы эту иерархию сломать. Значения и обоснования — в [docs/02_design.md](docs/02_design.md), раздел «Таймауты».

## Тесты и оценка качества

```bash
go test ./...                # юнит-тесты, база не нужна

go vet ./...

```

Интеграционные тесты отделены тегом сборки и требуют поднятой базы:

```bash
docker compose up -d db
TEST_DB_CONNECTION='postgres://user:password@localhost:5432/urlshortener?sslmode=disable' \
  go test -tags=integration ./...
```

Покрытие измерено по всему проекту: `go test -coverpkg=./... -coverprofile=cover.out ./...`, затем `go tool cover -func`. Разница между двумя числами — это `repository.Postgres` и пути сервиса, которые без живой базы не исполняются.

### Что покрыто

- **Контракт HTTP** — таблица кодов ответа из требований на заглушке сервиса: `415`, `413`, `400` и `422` по каждому виду негодного тела, `404`, `405` с заголовком `Allow`, редирект с точным значением `Location`, `503` с телом `degraded` при недоступной базе
- **Политика допустимых ссылок** — `javascript:` в двух видах, `ftp:`, относительный путь, ссылка с именем пользователя (`https://a.com@evil.example`), превышение длины
- **Правила системы** — идемпотентность, нормализация регистра схемы и домена, различие ссылок по финальному слэшу, повтор при коллизии кода, исчерпание попыток
- **Кэш** — попадание отдаёт ссылку, не обращаясь к репозиторию; параллельные промахи по одному коду сходятся в один запрос к базе через `singleflight`; недоступный Redis читается как промах и не меняет ответ
- **Различение уникальных ограничений** в хранилище: подмена одного поля даёт конфликт по коду, другого — по хешу
- **Конкурентное создание** — 50 параллельных запросов с одной ссылкой на хранилище в памяти и 20 против настоящей базы: все получают один код, в таблице одна строка. Второй тест — единственная проверка гонки **в базе**, `-race` её не видит

### Что не покрыто и почему

- `main` — проверяется прогоном `docker compose up` целиком, ради тестируемости не переписывался
- `cache.Redis` в части различения попадания и отрицательной записи — требует живого Redis; юнит-тестом проверен только отказ
- Совпадение имён ограничений в коде и в миграции — тест сравнивает константу с константой, расхождение поймал бы только интеграционный тест против изменённой схемы
