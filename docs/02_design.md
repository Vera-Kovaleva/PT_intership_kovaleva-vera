# Технический дизайн

Как я реализую требования, составленные в 01_requirements.md. Коды ответов, формат ошибки и инварианты данных здесь не переписываются — они заданы в 01_requirements.md, ниже только то, как они достигаются.

## Архитектура

Трёхслойная архитектура:

```
Handler → Service → Repository → PostgreSQL
             └────→ Cache      → Redis
```

- **Handler** — принимает HTTP запросы, разбирает и валидирует входные данные, формирует ответ
- **Service** — бизнес-логика: нормализация и валидация URL, хеширование, генерация кода
- **Repository** — работа с базой данных
- **Cache** — чтение и запись ссылок в Redis. Не слой, а вторая исходящая зависимость сервиса наравне с Repository: оба отдают ссылку по коду и друг о друге не знают. Сервис работоспособен без кэша

## Схема БД

```sql
CREATE TABLE urls (
    short_code   VARCHAR(6)  NOT NULL,
    original_url TEXT        NOT NULL,
    url_hash     BYTEA       NOT NULL,

    CONSTRAINT urls_pkey         PRIMARY KEY (short_code),
    CONSTRAINT urls_url_hash_key UNIQUE      (url_hash)
);
```

**Имена ограничений я задаю явно, а не оставляю на автогенерацию.** Это не косметика: обработка конфликтов различает, какое из двух ограничений сработало, по полю `ConstraintName` в ошибке (см. «Идемпотентность и гонки»). Если имя генерирует база, код начинает зависеть от того, как именно она его составила.

**Чего в схеме нет.** Отдельного `id`: код генерируется независимо и уникален сам по себе, поэтому суррогатный ключ не нужен, а `short_code` служит естественным первичным ключом. Отдельных `CREATE INDEX`: Postgres уже построил уникальные индексы под `PRIMARY KEY` (поиск при редиректе) и под `UNIQUE` (поиск при сокращении), а второй экземпляр того же индекса база обновляла бы при каждой записи и никогда не использовала. Времени создания — см. 01_requirements.md.

### Дедупликация по хешу

Инвариант «одному `original_url` соответствует не более одного `short_code`» я реализую через `url_hash`: сравнивается не полный текст ссылки, а её SHA-256, и на эту колонку стоит `UNIQUE`.

**Что гарантирует правильность.** Нормализация и хеширование выполняются **одной функцией**: она принимает сырой URL и возвращает нормализованную форму вместе с хешом. Отдельной функции «хеш от строки» не существует, поэтому посчитать хеш от ненормализованного значения негде. Вызывается она из единственного места, а тест фиксирует пары «ссылка → ожидаемый хеш».

Индекс напрямую по `original_url` не делаю: это TEXT произвольной длины, и на очень длинной ссылке Postgres откажется создать запись индекса — у B-tree предел ~2.7 КБ. Хеш храню как `BYTEA` (32 байта), а не hex-строкой `VARCHAR(64)`.

**Что может это сломать.** Связь между колонками база не проверяет — строку с хешом от посторонней ссылки она примет. Достаточно посчитать хеш в обход общей функции или по устаревшим правилам нормализации, и ссылка молча получит второй код. Поэтому «одна функция, одно место вызова» здесь единственный барьер.

**Чего не хватает на уровне базы.** Генерируемая колонка сделала бы рассинхронизацию невозможной, но Postgres требует `IMMUTABLE`-выражение, а `convert_to()` помечена `STABLE`:

```sql
-- отвергнуто: convert_to() не IMMUTABLE
url_hash BYTEA GENERATED ALWAYS AS (sha256(convert_to(original_url,'UTF8'))) STORED
```

Перейти ради этого на `IMMUTABLE`-функцию `md5()` нельзя: её коллизии подбираются намеренно, то есть чужая ссылка могла бы получить уже занятый код.

## Валидация URL

Способов проверить URL много; я выбрала разбор штатным `net/url`, а не строковые проверки (`strings.HasPrefix`, регулярное выражение, поиск подстроки) — ручной разбор регулярно пропускает процентное кодирование, часть с именем пользователя и особенности authority.

Порядок проверок:

1. Длина строки не превышает `MAX_URL_LENGTH` (2048 символов) — иначе `422`
2. `url.Parse` отработал без ошибки — иначе `422`. Управляющие символы, CR/LF и пробелы `net/url` отвергает сам
3. `u.IsAbs()` — ссылка абсолютная
4. `u.Scheme` ∈ {`http`, `https`} — закрытый список
5. `u.Host` не пустой
6. `u.User == nil` — имени пользователя и пароля в адресе нет

Смысл пунктов 4 и 6 — см. 01_requirements.md, «Политика допустимых ссылок».

## Нормализация URL

Из 01_requirements.md — ровно два правила: `u.Scheme` и `u.Host` приводятся к нижнему регистру. Учётные данные при этом не затрагиваются: в `net/url` они лежат в `u.User`, а не в `u.Host`.

Всё остальное не трогаю — путь, строку запроса, фрагмент, порт по умолчанию, порядок параметров: полная нормализация по RFC 3986 для этой задачи не нужна и добавила бы правил, способных изменить смысл адреса.

## Ограничение размера входных данных

Ограничений два: тело запроса — не больше 16 КБ (`http.MaxBytesReader`, превышение опознаётся по `*http.MaxBytesError` → `413`), длина URL — не больше 2048 символов (проверка в сервисном слое → `422`).

Назначение у них разное. Лимит тела ставлю до разбора, чтобы многомегабайтное тело не попало в память: он срабатывает даже если тело вообще не JSON, и таймауты тут не помогают — данные идут, чтение не висит. Лимит длины URL ограничивает то, что ляжет в `original_url` и в индекс. Лимит тела беру с запасом, чтобы допустимый URL не упёрся в него первым и не получил `413` вместо понятного `422`.

## Генерация кода

Код — 6 случайных символов base62 (`crypto/rand`), никак не связанных с самой ссылкой. Пространство — 62⁶ ≈ 56.8 млрд значений.

```
short_code = 6 случайных символов из [0-9a-zA-Z]
код в списке зарезервированных → сгенерировать заново
INSERT → конфликт UNIQUE по short_code → сгенерировать заново (до 3 попыток)
3 попытки исчерпаны → 500
```

**Исчерпание попыток я перевожу в `500`, а не повторяю до победы.** При 62⁶ значениях три подряд коллизии не могут быть невезением: это признак неисправности источника случайности или почти заполненной таблицы. Бесконечный цикл в таком состоянии удерживал бы соединение и горутину, поэтому запрос завершается ошибкой, а событие пишется в лог уровня `Error` с `request_id`.

### Почему не первые 6 символов хеша URL

Усечённый хеш выводится из ссылки детерминированно, и коллизию в нём разрешить нечем: выдать второй ссылке другой код нельзя — при следующем запросе система снова выведет тот же первый. А коллизии будут: по парадоксу дней рождений уже около 280 тыс. ссылок дают ~50% шанс совпадения. У случайного кода этого нет: конфликт ловит `UNIQUE`, повторная попытка берёт другое значение.

### Зарезервированные коды

ТЗ фиксирует формат короткой ссылки как `http://localhost:8080/abc123` — код лежит в корне пути, без префикса. Значит, развести пространства имён (например, отдавать редирект на `/r/{code}`) нельзя, и код теоретически может совпасть со служебным путём сервиса.

Резервирую **только строки длиной ровно 6 из алфавита base62** — других код не принимает. `shorten` (7 символов) и `favicon.ico` (точка не входит в алфавит) сгенерироваться не могут. А `health` может, и он уязвим: в `ServeMux` литеральный путь приоритетнее шаблона `/{code}`, поэтому такая ссылка сохранилась бы в базе и не открылась бы никогда.

Резервирую занятые сейчас и вероятные в будущем пути верхнего уровня, попадающие под это правило:

```
health, status, static, assets, public, robots, search, config, signup, logout
```

Проверка — поиск в map, O(1), в том же цикле, где обрабатывается коллизия.

## Маршрутизация и обработка нештатных запросов

Я использую `http.ServeMux` с шаблонами, включающими метод, и регистрирую три маршрута: `POST /shorten`, `GET /{code}`, `GET /health`.

В `go.mod` ставлю `go 1.27` — текущую версию. Минимум для шаблонов с методом — `go 1.22`, и включает их именно эта директива, а не версия тулчейна.

Поведение на нештатных запросах фиксирую здесь: сервер отвечает на каждый пришедший запрос независимо от того, писала я для него обработчик. Эндпоинтов по-прежнему два плюс служебный `/health`.

| Запрос | Ответ |
|---|---|
| `HEAD /{code}` | `302` без тела |
| `PUT /shorten`, `DELETE /shorten` | `405`, `Allow: POST` |
| `POST /{code}`, `DELETE /{code}` | `405`, `Allow: GET` |
| `GET /` | `404` |
| `GET /{code}/` (финальный слэш) | `404` |
| `GET /shorten` | `404` — попадает в `GET /{code}` с кодом `shorten`, в базе не находится |

`HEAD` обеспечивается маршрутизатором даром: шаблон с методом `GET` ловит и `HEAD`, тело Go обрезает сам.

### Почему 404 и 405 нельзя оставить на маршрутизатор

`ServeMux` отвечает `405` и `404` сам, но **тело пишет простым текстом**, и переопределить его нечем. Это нарушило бы единый формат ошибки из 01_requirements.md: клиент, разбирающий `error.code`, на этих двух статусах получил бы не JSON.

Поэтому я регистрирую catch-all `/`, который отвечает в общем формате:

```
путь /shorten  → 405, Allow: POST
путь /health   → 405, Allow: GET
иначе          → 404 not_found
```

Плата — автоматический `405` подавляется, и заголовок `Allow` я формирую сама. Путей мало, поэтому это десяток строк.

## Таймауты

| Таймаут | Значение | Зачем | Что видит клиент |
|---|---|---|---|
| ReadHeaderTimeout | 5с | чтение заголовков — защита от клиента, который тянет их бесконечно и держит соединение | соединение закрывается, HTTP-ответа нет |
| ReadTimeout | 5с | чтение всего запроса целиком, включая тело | соединение закрывается, HTTP-ответа нет |
| WriteTimeout | 5с | от конца чтения запроса до конца ответа, то есть потолок работы обработчика | соединение обрывается посреди ответа |
| IdleTimeout | 60с | сколько держим keep-alive соединение между запросами | простаивающее соединение закрывается, на запросы не влияет |
| Контекст запроса | 3с | передаётся в БД, по нему запрос реально отменяется | `503` |
| Запрос к базе данных | 2с | одна операция по индексу — единицы миллисекунд, 2с это уже большой запас | `503` |
| Graceful shutdown | 10с | не меньше потолка одного запроса, чтобы текущие успели завершиться | запросы, не уложившиеся в 10с, обрываются без ответа |

Иерархия: запрос к БД (2с) < контекст (3с) < WriteTimeout (5с) < shutdown (10с). Внутренний всегда строго меньше внешнего: при равных значениях клиента отрезало бы раньше, чем ошибка БД успела бы превратиться в ответ.

Значения выбирала от реальной работы: обе операции — поиск по индексу и вставка, единицы миллисекунд, так что 2с уже большой запас. Длинные таймауты не ставлю: каждый висящий запрос держит горутину и соединение к БД.

Отдельный таймаут ожидания свободного соединения из пула я не завожу: ожидание в `pgxpool` ограничивается контекстом, который передаётся в вызов, то есть уже покрыто контекстом запроса (3с). Отдельная настройка дублировала бы существующее ограничение.

`statement_timeout` на стороне Postgres не ставлю по той же причине: каждый вызов уходит в базу с контекстом, по которому pgx отменяет запрос, и серверный потолок дублировал бы уже существующее ограничение.

## Пул соединений

Размер пула я задаю явно, прямо в строке подключения (`pool_max_conns=10`), а не оставляю на умолчание. По умолчанию `pgxpool` берёт `max(4, число ядер)` — то есть поведение под нагрузкой отличалось бы на разных машинах и было бы невоспроизводимо.

Значение 10 — с запасом для одного экземпляра. Ограничение сверху — `max_connections` Postgres (по умолчанию 100) на все экземпляры вместе.

## Обработка ошибок

Все ошибки я привожу к ответу в одном месте — функция отображения ошибки на HTTP-ответ в слое Handler. Формат тела задан в 01_requirements.md.

| Причина | Как опознаётся | Ответ |
|---|---|---|
| Тело больше лимита | `*http.MaxBytesError` | `413` `payload_too_large` |
| `Content-Type` не JSON | проверка заголовка | `415` `unsupported_media_type` |
| Тело не разобралось в объект | ошибка декодера | `400` `malformed_json` |
| URL не прошёл валидацию | `ErrInvalidURL` | `422` `invalid_url` |
| Код не найден | `ErrNotFound` | `404` `not_found` |
| Метод не подходит пути | catch-all, см. «Маршрутизация» | `405` `method_not_allowed` |
| Истёк дедлайн запроса | `context.DeadlineExceeded` | `503` `service_unavailable` |
| База недоступна, пул не отдал соединение | ошибка подключения `pgconn` | `503` `service_unavailable` |
| Всё остальное | — | `500` `internal_error` |

**Middleware** выстроены в цепочку `RequestID → AccessLog → Recover → Timeout` снаружи внутрь. `AccessLog` стоит снаружи `Recover`, иначе упавший запрос не попадёт в лог доступа. `Timeout` — самый внутренний: он подменяет контекст запроса, а не пишет ответ сам, поэтому истёкший дедлайн доходит до общей функции отображения ошибок и отдаётся как `503` в стандартном формате.

Sentinel-ошибок завожу две — `ErrNotFound` и `ErrInvalidURL`: только под причины, пересекающие границы слоёв. Остальное Handler опознаёт у себя, и отдельные типы были бы лишними.

Правило, по которому я провела границу `500`/`503`, — см. 01_requirements.md.

**Панику** перехватываю middleware с `recover`: трассировка уходит в лог с `request_id`, клиенту — `500` со стандартным телом. Ни текста ошибки БД, ни трассировки, ни присланного URL в ответе: они выдали бы структуру таблиц, версию БД и пути на диске.

**Ушедшего клиента** (`context.Canceled` из контекста запроса) отказом не считаю: ответ не формирую, в лог пишу уровнем `Info`. `Canceled` и `DeadlineExceeded` различаю обязательно, иначе логи ошибок засоряются чужими отменами.

## Идемпотентность и гонки

Повторный `POST` с той же ссылкой возвращает тот же код — поиск по `url_hash`.

В таблице два уникальных ограничения, и конфликты по ним обрабатываются по-разному:

- по `url_hash` — это та же ссылка, которую параллельный запрос успел записать первым: не ошибка, читаем существующую запись и возвращаем её код
- по `short_code` — случайно совпали два сгенерированных кода: генерируем новый и повторяем вставку

Гарантию даёт UNIQUE, а не SELECT перед вставкой: запись может появиться в промежутке между SELECT и INSERT. SELECT оставляю как оптимизацию обычного пути.

Какое ограничение сработало, я различаю по структурированным полям ошибки, а не по тексту сообщения: текст зависит от локали и версии Postgres и может измениться, после чего обработка тихо сломается.

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) && pgErr.Code == "23505" { // unique_violation
    switch pgErr.ConstraintName {
    case "urls_url_hash_key":
        // та же ссылка: читаем существующую запись, возвращаем её код
    case "urls_pkey":
        // коллизия кода: генерируем новый и повторяем вставку
    }
}
```

Отсюда моё требование задавать имена ограничений явно в миграции — см. «Схема БД».

## Логирование

Я использую стандартный `slog` в JSON формате. Каждый запрос получает уникальный `request_id` через middleware.

**Что логируем:**

- Входящий запрос — метод, путь, `request_id`
- Время выполнения запроса и код ответа
- Результат — создан новый код или возвращён существующий
- Ошибки с контекстом
- Старт и остановка сервера

**Что логируем вместо самой ссылки:**

| Поле | Зачем |
|---|---|
| `short_code` | По нему нахожу запись в базе, когда нужен полный URL, — сам URL в логи не попадает |
| Хост целевой ссылки (`example.com`) | Видно, на какие домены сокращают; токенов и персональных данных в хосте не бывает |
| Длина URL | Полезна при отладке ограничений длины |

**Что НЕ логируем:**

- Полный оригинальный URL
- **Строку запроса (query-параметры) — никогда.** Именно там оказываются токены сброса пароля, идентификаторы сессий и персональные данные
- Тело запроса целиком

**Уровни:**

- `Debug` — детали для разработки, в проде выключен
- `Info` — нормальные события, включая уход клиента до ответа
- `Warn` — странное, но не критичное
- `Error` — отказы сервиса: паника, недоступность БД, исчерпание попыток генерации кода

## Кэширование

Переходов кратно больше, чем созданий, а `GET /{code}` — обычное чтение по ключу. Поэтому перед базой ставлю Redis по схеме cache-aside: ключ `url:{short_code}`, значение `original_url`. Префикс отделяет ссылки от всего, что может появиться в той же базе Redis позже.

- **Попадание** — отвечаю сразу, к базе не обращаюсь
- **Промах** — читаю из Postgres, записываю в Redis, отвечаю
- **При создании** ссылки сразу записываю её в кэш: она с большой вероятностью понадобится сразу — тому, кто её только что получил

**Инвалидации нет вообще:** ссылки не меняются и не удаляются, запись в кэше устареть не может. Это единственная причина, по которой кэш здесь настолько простой, и держится она ровно до появления удаления ссылок — тогда понадобится сброс ключа.

**Недоступный Redis — не ошибка.** Ошибку логирую и обращаюсь к Postgres, ответ клиенту не меняется: кэш не должен быть точкой отказа, иначе он снижает доступность вместо того, чтобы повышать. По той же причине `/health` Redis не проверяет — без кэша сервис работоспособен.

**Промахи кэширую тоже**, с коротким TTL (1 минута). Иначе перебор несуществующих кодов проходит мимо кэша целиком и нагружает Postgres напрямую — то есть кэш не покрывает именно тот случай, ради которого он в первую очередь нужен.

**Параллельные промахи по одному ключу объединяю через `singleflight`:** из множества одновременных запросов за одним кодом к базе уходит один, остальные ждут его результат. Действует он только в промежутке между первым промахом и записью в кэш — если запросы распределены во времени, объединять нечего, но тогда и нагрузки нет.

**TTL нужен не для актуальности, а чтобы Redis не рос бесконечно.** Ставлю `maxmemory` с политикой `allkeys-lru` и TTL с разбросом: без разброса ключи, записанные в один момент, истекут одновременно, и промахи придут одной волной.

## Последовательность обработки запроса

**Сокращение (POST /shorten):**

```
Handler ограничивает размер тела → разбирает JSON
→ Service нормализует и валидирует URL, считает хеш
→ Repository ищет запись по url_hash
→ найдена — Service возвращает существующий short_code
→ не найдена — Service генерирует код → Repository вставляет запись
   → конфликт по url_hash  — читаем существующую, возвращаем её код
   → конфликт по short_code — новый код, повтор (до 3 попыток)
→ Service кладёт ссылку в кэш
→ Handler отвечает 200
```

**Переход (GET /{code}):**

```
Handler принимает код → Service смотрит в Redis
→ попадание — Handler отвечает 302, Location = original_url, Cache-Control: no-store
→ промах — Repository ищет запись по short_code
   → найдена — кладём в кэш, отвечаем 302
   → не найдена — кладём в кэш отрицательную запись, отвечаем 404
→ Redis недоступен — идём сразу в Repository, пишем в лог
```

## API

### POST /shorten

**Запрос:**

```json
{"url": "https://example.com"}
```

**Ответ 200:**

```json
{"short_url": "http://localhost:8080/abc123"}
```

Короткую ссылку я собираю из `BASE_URL` и кода. Код состоит только из символов base62, поэтому экранирования не требует.

Коды ошибок и формат тела — см. 01_requirements.md, «Поведенческий контракт».

### GET /{code}

**Ответ:** `302`, заголовок `Location` — оригинальный абсолютный URL, взятый из базы.

`Location` формирую из проверенного и сохранённого значения, а не из пользовательского ввода и не конкатенацией строк — это рекомендованный OWASP паттерн.

Дополнительно отдаю `Cache-Control: no-store`: `302` и так не кэшируется по умолчанию, но явный заголовок снимает вопрос о промежуточных прокси и CDN.

Почему я выбрала `302` — см. 01_requirements.md.

### GET /health

Проверяет доступность базы (`pool.Ping`) с таймаутом 1с.

**Ответ 200:**

```json
{"status": "ok"}
```

**Ответ 503:**

```json
{"status": "degraded"}
```

Использую в `docker compose` как healthcheck сервиса. Смысл трёх состояний — см. 01_requirements.md, «Эксплуатационные требования».

## Конфигурация

Через окружение задаётся только то, что меняется от развёртывания к развёртыванию:

```env
BASE_URL=http://localhost:8080
DB_CONNECTION=postgres://user:password@db:5432/urlshortener?sslmode=disable&pool_max_conns=10
REDIS_ADDRESS=redis:6379
SERVER_PORT=8080
LOG_LEVEL=info
```

`BASE_URL` и `DB_CONNECTION` обязательны — без них сервис не стартует. Остальные имеют значения по умолчанию; пустой `REDIS_ADDRESS` означает работу без кэша.

**Таймауты, лимиты размеров и TTL кэша заданы константами в коде.** Их значения связаны иерархией (см. «Таймауты»), и возможность переопределить их снаружи позволила бы эту иерархию сломать — например, получить сервис, который рвёт соединение раньше, чем успевает сформировать ответ об ошибке. Это решения дизайна, а не настройки развёртывания.

## Безопасность

### Что я делаю

- Разбираю URL штатным `net/url`, не строковыми проверками
- Принимаю только схемы `http` и `https` по закрытому списку
- Отклоняю ссылки с именем пользователя — см. 01_requirements.md, «Политика допустимых ссылок»
- Ограничиваю размер тела и длину URL
- Беру адрес для редиректа из базы, а не из пользовательского ввода
- Не логирую полный URL и строку запроса
- Не отдаю в ответе ни текста ошибки БД, ни трассировки стека

**Не делаю ни одного исходящего запроса к сохранённой ссылке** — не проверяю доступность, не тяну заголовок страницы, значок и превью. Поэтому здесь нет SSRF: иначе присланный `http://169.254.169.254/latest/meta-data/` или `http://localhost:5432` заставил бы сервер сходить туда изнутри сети.

### Риски, которые я называю, но не устраняю

- **Сокращатель по природе — внешний редиректор:** человек не видит, куда попадёт, и домен сервиса одалживает доверие чужой ссылке. Свойство любого сокращателя. В production — страница-предупреждение перед переходом, списки доменов, репутационные проверки, отзыв ссылок, приём жалоб.
- **Перебор кодов:** случайный код снижает риск угадывания, но **не является механизмом аутентификации и авторизации**.
- **Ограничение частоты запросов:** `POST /shorten` можно слать в цикле. В production поставила бы лимит по IP; локально не тяну ради этого внешнюю зависимость.

## Тестирование

Перечень обязательных сценариев — в 01_requirements.md. Здесь только инструменты.

- **Unit** — стандартный пакет `testing`, табличные тесты для валидации URL, нормализации, генерации кода и функции «URL → хеш»
- **Моки** — интерфейс Repository мокируется в тестах сервисного слоя (ручной мок или `go.uber.org/mock`)
- **Интеграционные** — `POST /shorten` и `GET /{code}` против реальной PostgreSQL. Без testcontainers: тесты подключаются напрямую по `TEST_DB_CONNECTION` к базе, поднятой заранее — в CI это сервис `postgres` в пайплайне, локально `docker compose up -d db`. Перед прогоном применяются миграции. Отделены от unit build-тегом `integration` (`go test -tags=integration ./...`), чтобы обычный `go test ./...` не требовал поднятой БД
- **Редирект** — HTTP-клиент настраивается не следовать за редиректом (`CheckRedirect` возвращает `http.ErrUseLastResponse`), проверяются и статус, и точное значение `Location`
- **Конкурентное создание** — N горутин (`sync.WaitGroup`) одновременно отправляют `POST /shorten` с одним URL; проверяется, что все ответы содержат один код и в базе одна запись

- **`go test -race`** — гонки в памяти Go: незащищённая map, общий счётчик. Дубли в базе он не видит, их ловит тест конкурентного создания выше

## Сборка и запуск

```bash
cp .env.example .env
docker compose up
```

Сервис доступен на `http://localhost:8080`.

### Dockerfile

- Многоэтапная сборка: компилирую в образе с Go, в финальный образ копирую только бинарник
- `go.mod` и `go.sum` отдельным слоем до исходников — ради кэша зависимостей
- `CGO_ENABLED=0` — иначе бинарник не запустится в alpine
- Финальный образ `alpine`: в нём есть `wget` для healthcheck, в `scratch` и distroless его нет
- `USER nobody` — права root сервису не нужны
- Миграции в образ не копирую: SQL зашит в бинарник через `embed.FS`
- `.dockerignore` с `.git` и `.env`, чтобы пароль базы не попал в образ

### compose.yaml

Три сервиса: `db`, `redis` и `app`.

- `postgres:17-alpine` с точным тегом, не `latest` — иначе запуск невоспроизводим
- Healthcheck `pg_isready` у `db` и `depends_on: condition: service_healthy` у `app`: без этого сервис стартует раньше базы и уходит в перезапуск
- Именованный том под данные Postgres — иначе ссылки теряются при `docker compose down`
- Наружу публикую порт `8080` и порт базы: второй нужен интеграционным тестам
- `redis:7-alpine` с healthcheck `redis-cli ping`; том ему не нужен — кэш переживать перезапуск не обязан
- `depends_on` на `redis` ставлю без `service_healthy`: сервис работает и без кэша
- `restart: unless-stopped` у всех трёх
- Переменные берут из `.env`

### Миграции

```
migrations/
  0001_init.up.sql
  0001_init.down.sql
  embed.go
```

Имена в формате `golang-migrate`. `.down.sql` пишу всегда, даже если откатывать не планирую.

`embed.go` встраивает `.sql` в бинарник через `//go:embed` и держит функцию применения миграций. Без встраивания папку пришлось бы копировать в финальный образ и следить, чтобы путь совпадал с рабочим каталогом контейнера, — три места вместо одного.

Накатывает миграции сам сервис при старте, до начала прослушивания порта. Вариант с `docker-entrypoint-initdb.d` не выбрала: он срабатывает один раз при создании пустой базы, и после правки схемы у проверяющего осталась бы старая.

### .env

`.env` в `.gitignore`, в репозитории лежит `.env.example` с заглушками. Кроме переменных из раздела «Конфигурация» содержит `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` для контейнера базы — они должны совпадать с тем, что записано в `DB_CONNECTION`.

## Масштабирование

Сервис stateless, экземпляров может быть сколько угодно. Узкое место — Postgres: он один, и давление растёт с обеих сторон, со стороны чтения и со стороны записи.

Сейчас это закрыто кэшем перед базой и объединением параллельных промахов — см. «Кэширование». Такого решения хватает, пока нагрузка умещается в один экземпляр сервиса и один Postgres. За этой границей проявляются следующие ограничения.

**Соединения кончатся раньше пропускной способности.** Каждый экземпляр держит свой пул на 10 соединений, и при десяти экземплярах упирается `max_connections` Postgres — при том что сама база ещё не загружена. Решение — pgbouncer в режиме transaction pooling.

**Redis — единственный узел, и горячий ключ живёт на нём.** Отказ Redis сервис не роняет, но мгновенно переводит весь трафик чтения на Postgres: если кэш держал 90% чтений, база получает десятикратную нагрузку разом. Отдельно — вирусная ссылка даёт весь трафик в один ключ, и шардирование Redis не помогает, ключ один. Обе проблемы закрывает LRU-кэш в памяти процесса перед Redis.

**Чтение упирается в primary.** Решение — реплики для `GET /{code}`. Их цена — лаг репликации: ссылку создали и тут же по ней перешли, а на реплике записи ещё нет. Отдельной меры против этого не понадобится: ссылка при создании попадает в кэш и читается оттуда, до реплики не доходя. Гарантии это не даёт — если Redis в тот момент недоступен, запрос уйдёт на реплику и вернёт `404`.

**Объём данных перерастает один Postgres.** Решение — шардирование по `short_code`. Здесь оно дешевле обычного: все запросы идут по первичному ключу, межшардовых выборок нет.

**Перебор кодов проходит через весь стек.** Кэш промахов снимает нагрузку с базы, но запрос всё равно доходит до приложения. Решение — ограничение частоты по IP на входе; в «Безопасности» оно отмечено как нереализованное.
