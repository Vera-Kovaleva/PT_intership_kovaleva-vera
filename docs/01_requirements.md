# Требования

Что система делает, без технических решений. Технические решения — в 02_design.md.

## О системе

Сервис сокращения ссылок: превращает длинные URL в короткие коды и обратно.

Это сознательно **урезанная** система. ТЗ описывает два эндпоинта и приводит запрос и ответ каждого целиком — из этого я сделала вывод, что заданный контракт менять не следует, и приняла его как границу системы.

Что отсюда следует:

- **Авторизации нет.** Заголовки запроса в ТЗ не описаны, отдельного эндпоинта аутентификации тоже нет — значит, места для токена в заданном контракте я не вижу и не добавляю его.
- **Пользователи не различаются.** Тело запроса приведено как `{"url": "..."}`; поля `user_id` в нём нет, а добавить его означало бы изменить заданный контракт.
- **Отсюда — одна ссылка, один код.** Раз система не знает, кто сократил ссылку, одной ссылке соответствует ровно один код, общий для всех. С пользователями могло бы быть иначе — например, разные коды на один URL для разных рекламных кампаний.
- **Статистики нет, и времени в базе тоже.** Статистика переходов имеет смысл, когда есть кому её показывать, — владельца у ссылки нет. Без статистики дата создания ничего не даёт, а единственная полезная метка, время последнего использования, нужна только для удаления давно не нужных ссылок и тянет за собой механизм очистки, который вне скоупа.

## Use Cases

Пользователям системы — людям и внешним сервисам — доступны две возможности:

**1. Сократить ссылку.** Пользователь передаёт длинный URL и получает короткий код для него. Если такую ссылку уже сокращали, он получает тот же код, что и все остальные (см. «Идемпотентность»).

**2. Перейти по коду.** Пользователь передаёт короткий код, и система перенаправляет его на оригинальный URL.

Возможности между собой не связаны: сокративший ссылку и переходящий по ней — как правило, разные люди, и система их не различает.

Отдельно система отвечает на проверку работоспособности. Эта возможность адресована не пользователям, а обслуживающей стороне — см. «Эксплуатационные требования».

## Политика допустимых ссылок

Принимается ссылка, которая одновременно:

- **абсолютная** — относительный путь (`/foo`, `example.com`) не принимается;
- **со схемой `http` или `https`** — любая другая схема отклоняется;
- **с непустым хостом**;
- **без имени пользователя и пароля** в адресе;
- **не длиннее установленного предела** длины.

Про схемы: проверять только «есть схема» недостаточно — под такое условие проходят `ftp://example.com` и даже `javascript://example.com/…`, то есть ровно то, что я хочу отсечь. Поэтому я задаю закрытый список разрешённых схем.

Про имя пользователя и пароль: `https://www.paypal.com@evil.example` уводит браузер на `evil.example`, а выглядит как ссылка на первый домен. В сокращателе это опаснее обычного — короткая ссылка прячет адрес целиком, — поэтому такие ссылки отклоняю.

Система **не проверяет**, открывается ли ссылка: не запрашивает её, не загружает заголовок страницы, значок или превью. Я отказалась от этого сознательно — почему, разбираю в «Безопасности» в 02_design.md.

## Что может пойти не так

**Запрос сломан ещё до разбора данных:**

- Метод не поддержан для этого пути (например, `PUT /shorten`) — клиент получает «метод не разрешён» и список допустимых
- Тело больше допустимого размера — клиент получает «слишком большое тело», тело не читается целиком
- Тип содержимого задан и это не JSON — клиент получает «неподдерживаемый тип». Пустой заголовок пропускается: тогда работает обычная валидация тела
- Тело не разбирается как JSON или разобралось, но это не объект (`[1,2,3]`, `"строка"`, `null`) — полей нет, читать нечего, клиент получает ошибку разбора

**Данные разобраны, но не годятся:**

- Поле `url` отсутствует, пустое или не строка — клиент получает ошибку валидации
- Ссылка не проходит политику допустимых ссылок (не абсолютная, чужая схема, нет хоста, есть имя пользователя, слишком длинная) — клиент получает ошибку валидации, сохранение не происходит

**Ресурс не найден:**

- Короткий код не существует, имеет неверную длину или содержит недопустимые символы — клиент получает «не найдено», во всех трёх случаях одинаково

**Система не может обслужить:**

- База данных недоступна, либо запрос к ней не уложился в отведённое время — клиент получает «сервис временно недоступен», то есть «повтори позже»
- Непредвиденная ошибка или паника внутри обработчика — клиент получает «внутренняя ошибка». Подробности уходят только в лог; клиенту не показывается ни текст ошибки базы, ни трассировка стека
- Не удалось подобрать свободный короткий код за отведённое число попыток — клиент получает «внутренняя ошибка»: при таком размере пространства кодов это означает неисправность, а не невезение

**Клиент ушёл, не дождавшись ответа:**

- Соединение разорвано до того, как ответ отправлен — ответ не формируется, событие записывается в лог как ожидаемое, а не как ошибка сервера

## Поведенческий контракт

### Успешные сценарии

| Сценарий | Код |
|---|---|
| Сокращение ссылки — как для нового кода, так и для уже существующего | `200` |
| Переход по короткому коду | `302`, редирект на оригинальный URL |
| Проверка работоспособности, база доступна | `200` |

**Почему `200` в обоих случаях сокращения, а не `201` для нового кода.** Ответ клиенту идентичен — то же тело, та же ссылка, и на его дальнейшие действия не влияет, создана она сейчас или найдена существующая. Различать коды значило бы сообщать клиенту, что лежит в хранилище, чего контракт не обещает.

**Почему `302`, а не `301` или `308`.** Постоянный редирект клиент вправе закэшировать навсегда — тогда ссылку уже не отозвать, не перенацелить и не посчитать переходы. Выбрала временный, чтобы клиент приходил к сервису каждый раз.

### Ошибки

| Ситуация | Код | `error.code` |
|---|---|---|
| Метод не поддержан для этого пути | `405` | `method_not_allowed` |
| Тело больше допустимого размера | `413` | `payload_too_large` |
| `Content-Type` задан и это не `application/json` | `415` | `unsupported_media_type` |
| Тело не разбирается как JSON либо это не объект | `400` | `malformed_json` |
| Объект разобран, но значение `url` не годится | `422` | `invalid_url` |
| Короткий код не найден | `404` | `not_found` |
| База недоступна или запрос к ней не уложился в срок | `503` | `service_unavailable` |
| Непредвиденная ошибка или паника | `500` | `internal_error` |

**Граница между `400` и `422`:** `400` — не удалось получить объект с полями, разбирать нечего. `422` — объект получили, поле прочитали, значение не подходит. Клиенту это позволяет отличить «я неправильно собрал запрос» от «я прислал плохую ссылку».

**Граница между `500` и `503`:** `503` — всё, что связано с доступностью базы данных: нет соединения, не дождались свободного соединения, истёк срок запроса. Клиенту это означает «повтори позже, само пройдёт». `500` — всё остальное непредвиденное: паника, ошибка в коде, исчерпание попыток подбора кода. Клиенту это означает «повторять бесполезно».

**Про пустой `Content-Type`:** заголовок отсутствует — пропускаю и разбираю тело как JSON. Клиент, отправляющий запрос вручную, часто его не ставит, и отказывать ему нет причин: если тело окажется не JSON, это и так `400`, а если значение не годится — `422`. Проверяю только заданный заголовок: если он есть и это не JSON, клиент ошибся сознательно.

**Про `{"url": 123}`:** поле на месте, но значение не того типа. Формально разбор тела прерывается, однако по смыслу это «плохое значение», а не «сломанный запрос», поэтому ответ `422`, а не `400`.

### Формат ошибки

Все ошибки возвращаются одним форматом:

```json
{
  "error": {
    "code": "invalid_url",
    "message": "url must be an absolute http or https URL"
  }
}
```

`code` — машиночитаемый идентификатор, `message` — пояснение для человека. Список значений `code` закрыт: он целиком приведён в таблице выше и расширяется только вместе с этим документом.

`message` не содержит текста ошибок базы данных, трассировки стека и присланного пользователем URL.

## Идемпотентность

Я решила: если в системе уже есть точно такая же ссылка, система возвращает уже существующий для неё код, а не создаёт новый — иначе база бесконечно росла бы дубликатами одной ссылки под разными кодами.

**Цена моего решения.** Одна ссылка — один код на всех, кто её сократил. Значит, отозвать, отключить или перенацелить ссылку для одного отправителя невозможно: изменение затронет всех сразу. Для системы без пользователей это приемлемо — отличить отправителей всё равно нечем, — но при добавлении учётных записей я пересматривала бы это решение.

Как технически определяется, что ссылка уже встречалась, — см. 02_design.md.

## Нормализация URL

Ссылки, отличающиеся только регистром схемы или домена, считаю одной и той же: `HTTPS://Example.com/a` и `https://example.com/a` — один адрес. Основание — RFC 3986, где схема и хост объявлены регистронезависимыми.

**Регистр пути я не трогаю** — на многих серверах путь регистрозависим, и `/Doc` может быть другим документом, чем `/doc`.

**Финальный слэш я не убираю.** `https://example.com/docs/` и `https://example.com/docs` — разные ресурсы, за ними часто разный контент. «Поправив» адрес, я отправила бы человека не туда, куда он сдал ссылку, поэтому у меня это две разные ссылки с двумя разными кодами.

Приведение к единому виду применяется и при сравнении, и при сохранении, поэтому редирект всегда ведёт на адрес, отличающийся от присланного самое большее регистром схемы и домена.

Менять правила приведения после запуска нельзя: уже сохранённые ссылки сопоставлены по старым правилам и перестанут находиться — понадобится миграция с пересчётом.

## Зарезервированные коды

Некоторые короткие коды я исключила из выдачи: они совпали бы со служебными путями сервиса, и созданная ссылка оказалась бы недостижимой. Список зарезервированных значений и правило его формирования — см. 02_design.md.

## Инварианты данных

- `short_code` — не пустой, уникальный, не входит в список зарезервированных
- `original_url` — не пустой, соответствует политике допустимых ссылок
- Одному `original_url` соответствует не более одного `short_code`
- Уникальность `short_code` и отсутствие дублирующихся записей для одного URL — независимые друг от друга ограничения

## Эксплуатационные требования

Система отвечает на проверку работоспособности — её спрашивают оркестратор, балансировщик и проверяющий. Различаю три состояния:

| Состояние | Наблюдаемое поведение | Что делать наблюдателю |
|---|---|---|
| Сервис не запущен или упал | Соединение не устанавливается, HTTP-ответа нет вовсе | Перезапустить |
| Сервис работает, база доступна | `200`, статус `ok` | Слать трафик |
| Сервис работает, база недоступна | `503`, статус `degraded` | Трафик не слать, но и не перезапускать — проблема не в сервисе |

Проверку, отвечающую `ok` независимо от состояния базы, не делаю: она вводит в заблуждение, когда сервис не может обслужить ни одного запроса.

## Тестирование

Что должно быть проверено (конкретные инструменты и подходы — см. 02_design.md):

- **Unit** — валидация URL, нормализация, генерация кода
- **Моки** — бизнес-логика (сервисный слой) должна быть проверяема независимо от реальной базы данных
- **Интеграционные** — сценарии сокращения и перехода должны быть проверены на реальной БД
- **Race condition** — при параллельных запросах с одним и тем же URL все запросы должны получить один и тот же короткий код, без создания дублей

### Обязательные сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Валидный `POST /shorten` | `200`, непустой `short_url`, запись сохранена |
| Повторный `POST /shorten` с той же ссылкой | `200`, тот же код, новой записи не появилось |
| Ссылки, отличающиеся регистром схемы и домена | Один и тот же код |
| Ссылки, отличающиеся финальным слэшем | Разные коды |
| Тело не разбирается как JSON | `400` |
| Тело — валидный JSON, но не объект (`[1,2,3]`) | `400` |
| Поле `url` отсутствует | `422` |
| `url` — пустая строка | `422` |
| `url` — не строка (`{"url": 123}`) | `422` |
| `javascript:alert(1)` | `422` |
| `javascript://example.com/%0aalert(1)` | `422` — схема не в списке разрешённых |
| `ftp://example.com` | `422` |
| Относительный путь `/foo` | `422` |
| Ссылка с именем пользователя (`https://a.com@evil.example`) | `422` |
| Ссылка длиннее предела | `422` |
| Тело больше предела | `413` |
| `Content-Type` задан и не JSON | `415` |
| `Content-Type` пустой, тело валидно | как обычно: `200` |
| `Content-Type` пустой, `url` не годится | `422` |
| `PUT /shorten`, `POST /{code}` | `405` с заголовком `Allow` |
| Корректный `GET /{code}` | `302` и **точное** значение заголовка `Location` |
| `HEAD /{code}` | `302`, заголовки как у `GET`, тело пустое |
| Неизвестный код | `404` |
| Код неверной длины или с недопустимыми символами | `404` |
| `GET /` | `404` |
| `GET /{code}/` (финальный слэш) | `404` |
| Параллельные создания одной ссылки | Один и тот же код у всех, одна запись в базе |
| `GET /health` при недоступной базе | `503`, статус `degraded` |

Тест редиректа проверяет **и статус, и точное значение `Location`**, а HTTP-клиент в нём не следует за редиректом: иначе он уйдёт на целевой сайт и правильность заголовка останется непроверенной.

## Вне скоупа

Я сознательно не реализую в рамках текущей системы:

- Авторизация и аутентификация пользователей
- Пользовательские алиасы для коротких ссылок
- Счётчик переходов и аналитика
- Endpoint для управления своими ссылками (просмотр, изменение, удаление)
- TTL и автоматическое удаление старых ссылок
- Ограничение частоты запросов
- Проверка доступности ссылки и любые исходящие запросы к ней
- Проверка ссылок на вредоносность, страница-предупреждение перед переходом, списки разрешённых и запрещённых доменов
